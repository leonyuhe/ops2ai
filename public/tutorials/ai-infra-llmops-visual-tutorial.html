00ORIENTATION
Start here · 先把两个词分开

AI Infra 是栈，LLMOps 是生命周期

它们经常出现在同一场面试、同一张架构图里，却不是同一层东西。AI Infra 关心“计算怎么跑得快、稳、省”；LLMOps 关心“模型产品怎么评测、发布、观测、迭代”。一个偏系统，一个偏运营；在部署与观测处深度重叠。

The one-sentence difference

AI Infra 是“发电厂、道路和工厂设备”，LLMOps 是“车队调度、质检和客服”。没有前者，模型跑不起来；没有后者，模型跑得再快，也可能在线上给出错误、过时或不合规的答案。

Common confusion

“LLMOps 就是 prompt engineering？”

不是。Prompt 只是被管理的一个版本化产物。LLMOps 还要处理评测集、发布门禁、线上质量、安全策略、反馈闭环与事故响应；它更接近“LLM 产品的持续交付与运营”。

Relationship

MLOps ⊃ LLMOps，但 AI Infra 在更下面

MLOps 是更广的 ML 生命周期实践；LLMOps 是它在生成式模型上的特化。AI Infra 不是生命周期，而是支撑所有 ML 工作负载的技术栈。两者是不同维度，不是二选一。

01THE STACK
AI Infra · 从硅到产品

AI Infra 不是一堆 GPU，而是一条数据通路

一块 GPU 只有在电力、互联、存储、调度和运行时都接对的时候，才会变成可用算力。任何一层掉链子，上层看到的都只是“慢”和“不稳定”。

AI Infra 的职责可以概括成一句话：把模型计算的物理约束，翻译成上层可用的吞吐、延迟、可靠性和成本。它不只是采购硬件，也包括让多张卡协同、让任务排队、让故障恢复、让推理请求被高效地拼在一起。

Compute

算力不是吞吐

FLOPS 是峰值；真实吞吐还取决于内存带宽、kernel 效率、批大小和通信。峰值利用率 100% 往往只是营销数字。

Memory

显存是硬约束

模型、梯度、优化器状态、激活和 KV Cache 都在抢同一块 HBM。显存不够，再快的卡也只能换并行策略。

Fabric

通信会吃掉线性扩展

多卡不是简单相加。All-Reduce、All-to-All、流水线气泡会把“8 卡 = 8 倍”打成“8 卡 = 4.7 倍”。

Latency hierarchy

不同层级的访问，差了好几个数量级

log scale · 示意

这就是为什么“把数据搬来搬去”常常比“算”更贵。AI Infra 的很多设计，本质是在减少数据移动。

Infra lens

看到一个新模型，不要只问“多少参数”。还要问：权重多大、每 token 要读多少 HBM、跨卡通信多少、batch 能开多大、故障恢复要多久。这些问题决定了它能不能变成产品。

02PERFORMANCE
AI Infra · 性能的第一性原理

Roofline：
你到底卡在算力，
还是卡在搬数据？

同一块 GPU，跑不同的算子，瓶颈可能完全不同。Roofline 用一条简单的上界告诉你：可达性能 = min(峰值算力, 算术强度 × 内存带宽)。

算术强度（arithmetic intensity）是每读/写 1 字节数据，做了多少次浮点运算（FLOP/Byte）。强度低，算得少、搬得多，就会被内存带宽卡住；强度高，搬得少、算得多，才会接近峰值算力。两条线的交点叫 ridge point，是这台机器的“性格分界”。

Decode

内存带宽受限

自回归每生成一个 token，要把大量权重从 HBM 读一遍。算术强度接近 1，GPU 算力大量闲置，所以 KV Cache、量化和 batching 才关键。

Prefill / Training

更容易算力受限

大矩阵乘可以复用权重和激活，算术强度高，能接近峰值。此时要关心 Tensor Core 利用率、kernel 融合和通信重叠。

The lever

提高复用，或减少搬运

batch、tiling、算子融合提高数据复用；量化、稀疏、KV 压缩减少字节数。两条路都在把工作点往右上角推。

Do not memorize one number

Roofline 是上界，不是实测。真实性能还会被 kernel 启动、调度、通信、cache 命中、Tensor Core 形状约束拉低。它的价值是帮你判断“优化方向”：先搬数据，还是先算得更满。

03SCALE OUT
AI Infra · 从一张卡到一万张卡

并行不是“多插几张卡”，而是切分计算与通信

模型太大、数据太多、单卡太慢，于是我们把计算切到多张 GPU 上。切法不同，显存、通信和实现复杂度就不同。核心问题只有一个：每次切分，换来多少显存节省，付出多少通信？

数据并行（DP）复制模型、切分 batch；张量并行（TP）切分同一层的矩阵；流水并行（PP）把不同层放到不同卡上，像工厂流水线；ZeRO 则把优化器状态、梯度、参数分片，减少每张卡的冗余。大模型训练通常是 DP × TP × PP 的组合，MoE 还会加上专家并行（EP）。

Collective

Ring All-Reduce 为什么快？

每个 GPU 只和左右邻居交换数据，把全量 All-Reduce 拆成 2(N−1) 步。它不减少总通信量，但把流量均匀摊到环上，避免单点拥堵。

The topology rule

把通信放在最快的那条线上

TP 的 All-Reduce / All-Gather 每层都发生，尽量放在 NVLink 域内；PP 的激活传递跨 stage；DP 的梯度 All-Reduce 可以跨节点，但会吃满 RDMA。

world_size = DP × TP × PP × EP

如果拓扑和并行策略不匹配，GPU 会一边算一边等网络；把“8 卡线性加速”打成 4 倍甚至更低。

The trade-off

并行不是免费的。每多切一刀，就多一次通信、多一个失败点、多一层调度复杂度。好的并行策略不是“切得最细”，而是让计算、显存、通信三者同时落在可接受区间。

模型本身

BF16 下权重约 2P bytes，梯度再一份 2P。70B 模型光这两项就约 280GB，单卡已经放不下。

Optimizer states

Adam 的 m、v 和 FP32 master weights 常占 12P bytes。ZeRO-1 首先分片的就是它，收益最大。

Activations

随 batch × seq 增长

激活取决于层数、序列长度、batch 和 checkpointing 策略。长上下文训练时，它往往比参数更先爆。

Inference is different

推理没有梯度和优化器状态，但有 KV Cache。上下文越长、并发越高，KV Cache 越像“第二组模型权重”。第 05 章会看到它如何决定推理服务的 batch 和吞吐。

05SERVING
AI Infra · 推理引擎

连续批处理：让 GPU 不再等最慢的那个请求

推理服务不是“一次算一个请求”。把多个请求拼成 batch 能提高吞吐，但静态 batch 会被最长的请求拖住。连续批处理在任意请求结束时立刻补位，把 GPU 的空闲时间压到最低。

GPU 利用率—slot occupancy

Why it matters

吞吐与延迟不是同一个指标

静态 batch 追求“把一次矩阵乘做大”，但短请求必须陪跑长请求，尾延迟变差。连续批处理让新请求在 tick 边界插入，GPU 利用率更高，P95 延迟更低。

代价是调度器要管理每个序列的 KV Cache、位置和生命周期；这也是 vLLM、SGLang、TensorRT-LLM 等推理引擎的核心战场。

PagedAttention：把 KV Cache 切成固定大小的 page，按需分配，像操作系统管理虚拟内存。它减少碎片和预留，让更多序列同时驻留。

Serving lens

用户感知的是 P95，不是平均吞吐。一个推理引擎要同时优化：首 token 延迟、每 token 延迟、吞吐、显存、公平性和成本。批处理只是其中一把旋钮。

06ACCELERATE
AI Infra · 推理加速

压缩与投机：用更少的字节，换更快的 token

推理的瓶颈常常不是“算不动”，而是“搬不动”和“等太久”。量化减少每个权重占用的字节，投机解码让一次大模型前向验证多个草稿 token，蒸馏则把能力搬到更小的学生模型。

Speed is not free

三种加速，三种代价

量化：把权重/激活压到更低位宽，减少 HBM 读写，通常直接提升 decode 吞吐；代价是精度、校准和 kernel 支持。

投机解码：小 draft 模型快速起草，大模型并行验证；草稿命中率越高收益越大，草稿模型本身也占显存。

蒸馏：用大模型教小模型，把能力迁移到更便宜的学生模型；适合固定任务，但上限受学生容量限制。

Quantization

先量化权重，还是激活？

权重更容易离线量化；激活是动态的，需要校准和 scale。W8A8 / W4A16 是常见组合，能否加速取决于 GPU 是否有对应低比特 kernel。

Speculative

草稿命中率决定收益

如果 draft 模型和 target 分布差太远，验证后大量拒绝，反而浪费算力。它适合“简单续写多、难 token 少”的工作负载。

Distillation

把大模型装进小模型

学生模型学的是老师的输出分布或中间表示。它可以显著降低部署成本，但需要高质量数据和再训练，不是免费午餐。

Measure, don't assume

所有加速都要在真实 workload 上测 P95 和单位成本。量化可能让某些算子变慢；投机在低 batch 下才明显；蒸馏会改变能力边界。AI Infra 的优化目标是端到端指标，不是某个 kernel 的峰值。

07RELIABILITY
AI Infra · 万卡训练的真正难点

可靠性：GPU 会坏，任务不能从头再来

在万卡规模上，硬件故障不是“例外”，而是日常。真正重要的指标不是“从没坏过”，而是 goodput：扣掉故障、重启、等待和排队之后，集群到底交付了多少有效训练时间。

大模型训练通常要持续数天到数月。一个节点掉线、一次 ECC 错误、一条网络抖动，都可能让整个任务停住。Checkpoint 把模型状态定期写到存储；故障发生后，任务从最近的 checkpoint 恢复，而不是从第 0 步开始。恢复越快、checkpoint 越聪明，goodput 越高。

一次 70% 处的故障，如果最近 checkpoint 在 64%，就损失 6% 的训练；恢复还要时间。缩短间隔能减少回滚，但会增加 I/O 与存储成本。

Failure

故障是分布，不是事件

GPU、网卡、光模块、电源、存储都会坏。规模越大，MTBF 越短；系统必须假设“总会有东西坏”，而不是祈祷不出错。

Recovery

恢复时间是成本

重启、重新加载 checkpoint、重建通信组、重新 warmup 都要时间。恢复 5 分钟和 50 分钟，对 goodput 的影响完全不同。

Scheduling

抢占与碎片

Spot 实例便宜但会被回收；gang scheduling 保证整组资源同时到位；拓扑感知调度避免把通信频繁的卡放到远处。

回滚能在分钟级完成吗？

LLMOps 的核心不是“让模型上线”，而是让每一次变更都有证据、有边界、有退路。

LLMOps ≠ model training

LLMOps 不负责把 GPU 利用率从 60% 提到 80%，也不负责设计 All-Reduce。它负责定义“什么叫好”、证明“这次变更没有变坏”、并在线上持续发现新的 bad case。它依赖 AI Infra，但不替代 AI Infra。

The bridge metric

每百万 token 成本是 AI Infra 与 LLMOps 的天然桥梁：Infra 决定分母（吞吐、利用率、量化），LLMOps 决定分子（路由、缓存、上下文长度、输出长度、重试）。任何一方单独优化，都可能把账单推给另一方。

Glossary · 随手查
AI Infra

支撑 AI 工作负载的硬件、网络、存储、调度、训练/推理运行时与可靠性工程。核心指标是吞吐、延迟、利用率、故障恢复与单位算力成本。

LLMOps

面向 LLM 产品的生命周期运营：版本、评测、发布、灰度、观测、安全、反馈与回滚。它是 MLOps 在生成式模型应用上的特化。

MLOps / LLMOps

MLOps 是更广的 ML 系统生命周期实践；LLMOps 是它在生成式模型应用上的特化，额外强调 prompt、评测、RAG / Agent、幻觉与安全。

Roofline

用算术强度与内存带宽估计性能上界的模型：可达性能 = min(峰值算力, 算术强度 × 带宽)。

ZeRO

把优化器状态、梯度、参数分片到多张 GPU 上，减少每卡冗余；stage 1/2/3 分别切优化器、梯度、参数。

KV Cache

自回归推理时缓存历史 token 的 Key/Value，避免重复计算。它随上下文长度、层数、并发增长，是推理显存的主要开销之一。

Continuous batching

请求在 tick 边界动态加入/退出 batch，短请求结束后立即让新请求补位，提高 GPU 利用率并降低排队。

Goodput

扣掉故障、重启、排队和无效计算后，集群实际交付的有效训练/服务吞吐。比“峰值利用率”更接近业务价值。

Canary / Eval Gate

灰度发布与发布门禁：先把新版本给一小部分流量，用评测与线上指标证明没有变坏，再扩大或回滚。
