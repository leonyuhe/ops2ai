> GPU 很贵，让它等数据是最昂贵的浪费。存储 I/O 优化的目标只有一个：喂得比算得快。

## 数据加载管道：别让 GPU 等数据

典型管道：对象存储/共享盘 → DataLoader 读取解码 → 预处理 → 送显存。每一环都可能卡：

- **num_workers**：CPU 并行加载进程数，调到 GPU 不再饥饿为止（常见 4-16）。
- **pin_memory=True + 异步拷贝**：CPU 内存锁定页，H2D 传输才能与计算重叠。
- **prefetch**：提前取下一个 batch。
- **预处理尽量搬上 GPU** 或离线预处理好——CPU 做图像解码/增强是常见瓶颈。

判据：Nsight Systems 时间线上 step 之间的 GPU 空白 = 数据饥饿的铁证。

## 数据放置：I/O 层级决策

| 数据形态 | 推荐位置 | 理由 |
| --- | --- | --- |
| 热训练集（反复读） | 本地 NVMe 或内存缓存 | 每 epoch 都读，网络盘会成瓶颈 |
| 温数据 | 高性能共享文件系统（Lustre/GPFS）或对象存储 | 容量与共享的平衡 |
| Checkpoint | 本地 NVMe 缓冲 → 异步上传对象存储 | 写出要快，落盘要稳 |

## Checkpoint：省显存的事少做，省时间的事多做 ★

大模型 checkpoint 动辄几百 GB，写出本身就是工程：

- **异步 checkpoint**：先写本地内存/NVMe，训练不停，后台线程上传远端——同步写远端对象存储等于每 N 步主动暂停训练几分钟。
- **分片保存**：FSDP/ZeRO 下状态本来就分片，直接按分片存，加载时再拼——比聚合存一份快得多。
- **保留策略**：磁盘配额 + 滚动保留最近 K 个 + 关键里程碑长期归档。checkpoint 挤爆磁盘导致训练中断是真实高发事故。
- **定期演练恢复**：只写不练恢复的 checkpoint 系统等于没有——和备份系统同理。

## 数据预处理管线的一次性投入

tokenize、清洗、格式转换这些预处理，离线一次做好存成二进制格式（带索引），训练时直接流式读——不要每个 epoch 重复 tokenize 几 TB 文本。这和数仓里"ODS 一次、DWD 复用"的思想一致。

## 监控要点

- DataLoader 等待时间占比（训练框架打点）
- Checkpoint 写出耗时与成功率（告警项）
- 本地盘水位（checkpoint + 缓存）——>85% 告警
