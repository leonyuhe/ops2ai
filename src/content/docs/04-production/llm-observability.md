> 好消息：可观测性是运维转型 AI 最短的桥。坏消息：AI 服务多了一层传统监控没有的维度——质量。

## 四层指标体系

### 第一层：资源层（你已会）

GPU 利用率、显存占用、温度、功耗（DCGM Exporter）。注意解读差异：decode 主导的推理负载 GPU-Util 天然偏低，看显存带宽占用更有信息量。

### 第二层：引擎层

vLLM/SGLang 自带的 Prometheus 指标：

- `running` / `waiting` 请求数：实时并发与排队深度
- KV Cache 使用率：容量水位，接近 100% 必然排队
- prefill/decode 的 token 吞吐：引擎健康度

### 第三层：延迟与 SLO 层

- **TTFT** 和 **TPOT** 分开看分位数（p50/p95/p99），别平均——平均值在长尾场景是谎言。
- 拆解归因：网关耗时、排队耗时、prefill 耗时、decode 耗时，每一段单独打点，p99 翻倍时你能 5 分钟定位到段。

### 第四层：质量与成本层（AI 特有）

- **token 账本**：按应用/租户/模型分维度的 input/output token 计数——这是成本归因和计费的原始数据。
- **质量回归**：固定评测集定时跑分，prompt 或模型版本变更前后对比。准确率漂移 2 个点比延迟漂移更致命，也更隐蔽。
- **业务信号**：答案采纳率、重试率、用户改写率——质量问题的最早信号往往在用户行为里。

## 告警设计原则

- 延迟类：TTFT/TPOT p95 超 SLO 即告警（同你传统经验）。
- 容量类：KV Cache 水位 + 队列长度组合告警，单看利用率会漏报。
- 质量类：评测分数下降走工单而非页面告警——它需要人工判断，不该半夜叫醒人。
- 成本类：token 消耗环比异常（昨日 3 倍）告警——通常意味着某个调用方死循环了。

## 一个真实的排障剧本

现象：发布后 p99 TTFT 从 1.2s 涨到 3s，模型未变更。

排查顺序（照抄可用）：

1. 看队列：waiting 是否变长 → 是则容量问题，否则往下看。
2. 看 KV Cache 水位：是否因更长上下文配置导致并发容量下降。
3. 拆段耗时：排队/prefill/decode 哪段涨了。
4. 看变更：prompt 模板变长？max_tokens 调大？前缀缓存失效（system prompt 改了导致缓存全 miss）？
5. 看流量：是否有新调用方带来了超长输入。

这个剧本覆盖了 80% 的推理延迟事故。它的骨架就是你排 Nginx 变慢时的那套：队列 → 资源 → 分段耗时 → 变更 → 流量。
