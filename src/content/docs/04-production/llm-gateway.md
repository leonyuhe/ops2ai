> LLM 网关是 API 网关的直系后代：路由、认证、限流、熔断全都熟悉，新增的考点是 token 计费、语义缓存和质量护栏。

## 为什么需要网关层

直连模型服务的问题：多模型多供应商无统一入口、密钥散落各应用、成本无法归账、故障没有退路。网关把这些收敛到一层——和当年微服务网关收敛服务治理一模一样。

## 核心功能清单 ★

### 1. 路由与分级

- 按模型路由：简单问题 → 小模型，难题 → 大模型（成本杠杆第一名）。
- 按租户/应用路由：配额隔离，互不争抢。
- 按合规路由：敏感数据走本地模型，非敏感走云端 API。

### 2. 限流：从请求数到 token 数 ★

传统限流按 QPS；LLM 限流必须按 **token 速率**——一个 8K 长输入请求顶一百个短请求的成本。实现上是令牌桶的变体：令牌 = token 数而非请求数。配额维度：用户/应用/模型三维。

### 3. 故障转移

- 供应商级熔断：某家 API 超时/429/5xx 超阈值 → 自动切到备用供应商或本地模型。
- 降级链设计：大模型超时 → 小模型兜底 → 缓存答案兜底 → 友好错误。每一级都要提前演练。

### 4. 语义缓存

- 精确缓存：相同 prompt 直接命中（便宜但命中率低）。
- 语义缓存：embedding 相似度超过阈值即命中历史答案——命中率高一档，但要防"近似问题拿了错误答案"，阈值要用评测集调，且敏感场景禁用。

### 5. 成本治理（运维的新主场）

- 全量记录 usage（input/output token × 模型单价）进数仓。
- 按应用出日报：哪个团队在烧钱、哪条链路 token 暴涨。
- 预算闸：应用级月预算，超限自动降级到小模型或告警——GPU 时代的"费用保护"。

### 6. 安全与护栏

- 入站：提示词注入检测、敏感信息（PII）脱敏。
- 出站：有害内容过滤、事实性抽检。
- 审计：全量请求/响应留痕（加密存储、访问受控）——合规刚需。

## 开源方案与自建

- 现成方案：LiteLLM、Kong AI Gateway、Higress AI 插件等可直接起步。
- 自建理由：路由策略深度定制、与内部 SSO/计费系统打通。
- 无论哪种：**网关本身要低延迟**——它不该成为 TTFT 的大头；流式响应必须端到端透传（SSE 不能被网关缓冲截断）。

## 容量与可用性

网关自身是无状态服务，按 CPU 横向扩即可；但它聚合了所有后端的健康状态，是把"多模型多供应商"抽象成单一可靠服务的关键层——监控它到各后端的错误率和延迟分布，等于给整条 AI 链路装了总电表。
