> 容量规划是你运维生涯里最值钱的技能之一。在 AI 时代它值更多钱——因为 GPU 卡时的单价是 CPU 的几十倍，算错账的代价也大了几十倍。

## 规划流程五步法

### 第一步：定义负载画像

不要只问"多少 QPS"，要收集完整的负载特征：

- 平均输入/输出 token 数（决定单请求算力消耗）
- QPS 均值与峰值、峰值时段
- 上下文长度分布（短问答 vs 长文档分析是两种动物）

### 第二步：定 SLO

- TTFT p95（首字延迟）：聊天场景建议 < 2s
- TPOT p95（逐字速度）：> 20 token/s（快过人阅读速度）
- 可用性目标：几个 9

### 第三步：单卡基准测试

在目标卡型上用 vLLM 起服务，用 `vllm bench` 阶梯加压：

- 画出"并发数 vs TTFT/TPOT"曲线
- 找到拐点：SLO 刚好不被违反的最大并发数，就是**单卡容量**
- 记录该点的吞吐（token/s）

### 第四步：算卡数

```
卡数 = 峰值 QPS ÷ 单卡容量 × 冗余系数(1.3~1.5) × 可用性副本
```

冗余系数的理由和你做 Web 容量规划一样：留头部空间应对突发、滚动升级、单机故障。

### 第五步：成本复核与杠杆

按推理成本核算的方法算出月成本，太贵就拉杠杆：量化、换小模型、提高单卡并发。

## 一个完整案例

需求：客服助手，峰值 20 QPS，平均输入 1500 token、输出 200 token，SLO 要求 TTFT p95 < 2s。

1. 负载画像：短输入短输出，标准聊天场景。
2. 单卡实测：7B FP16 模型在 L40S 上，连续批处理下 50 并发时 TTFT p95 约 1.5s——单卡容量 50 并发。
3. 算卡数：20 QPS × 平均请求时长（1500 prefill + 200 decode ≈ 10s）≈ 200 并发需求 → 200 ÷ 50 = 4 卡 × 1.3 冗余 ≈ 6 卡，再加 1 副本 = 7 卡。
4. 复核：7 张 L40S 月成本约数万元——如果太贵，INT4 量化后单卡容量提升，可能 4 卡就够。

注意这里的关键换算：**QPS × 请求时长 = 并发数**（Little's Law，你在 Web 容量规划里就用过它，一字不改地适用）。

## 规划中的三个经典错误

1. **用均值规划**：按平均 QPS 买卡，峰值一来全线排队。永远按峰值 + 冗余规划。
2. **忽略上下文增长**：上线后用户输入越来越长（上传文档、多轮对话），KV Cache 需求超规划。留显存余量，监控上下文长度分布的漂移。
3. **不留实验余量**：模型版本升级（更大模型、更长上下文）必然发生。机位、电力、预算都留一档。
