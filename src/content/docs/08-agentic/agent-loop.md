> Agent = LLM + 工具 + 循环。 demo 一天能写出来，可靠地跑在生产上才是真功夫——本文讲可靠性的部分。

## Agent 循环的最小骨架

```
while 未完成 and 步数 < 上限:
    观察当前状态（上下文）
    模型决策：调用工具 or 输出最终答案
    执行工具，结果写回上下文
    记录每一步（trace）
```

每一步都可能失败——工程的全部内容就是让这个循环**可终止、可恢复、可审计**。

## 工具设计：LLM 能用对的工具才是好工具 ★

- **数量克制**：工具几十个时模型选择错误率显著上升。宁要 10 个职责清晰的工具，不要 50 个互相重叠的。
- **schema 即文档**：参数名、描述、示例都要写给模型看（"start_date：ISO 格式日期，如 2026-01-31"）。
- **返回值要模型友好**：返回结构化摘要而非原始大 JSON——超长返回挤爆上下文还稀释注意力。
- **幂等设计**：工具可能被重试调用，写操作必须幂等（带 idempotency key）。

## 错误恢复三件套

1. **工具层重试**：超时/限流做指数退避重试，错误信息返回给模型让它换参数（"401 认证失败"这种要明明白白写给模型）。
2. **循环层兜底**：模型连续 N 步无进展（重复调用同一工具同样参数）→ 打断并降级。
3. **预算硬墙**：最大步数、最大 token 消耗、最长 wall-clock 时间——三者都设上限，防止失控循环烧钱。

## 关键写操作必须过"人在回路"

删除、支付、发送这类不可逆操作：Agent 提出动作 → 人类审批 → 才执行。实现上是循环里的一个特殊工具"请求审批"，异步等待人工确认。原则：**模型可以提议，代码才能批准**。

## 失效模式与对策

| 失效模式 | 对策 |
| --- | --- |
| 死循环/兜圈子 | 步数上限 + 重复检测 |
| 中途漂移（做着做着忘了目标） | 定期把原始目标重述进上下文；长任务拆子目标 |
| 工具幻觉（编造不存在的工具/参数） | 约束解码 + 调用前 schema 校验 |
| 上下文爆炸 | 工具结果摘要化、旧步骤压缩 |

## 运维视角

Agent 是"会自己决策的分布式系统客户端"——你的服务治理经验（超时、重试、熔断、幂等、配额）全部适用，而且因为调用方是不确定的模型，这些纪律要比人工调用时代更严格。
