> Prefill 拼算力、Decode 拼带宽——两种资源画像完全不同的负载挤在同一引擎里，天然互相伤害。PD 分离就是让它们各住各的房子。

## 问题：混部干扰

同一 GPU 上 prefill 和 decode 混合调度时：

- 一个长 prefill 进来，decode 被抢占几百毫秒 → 在线用户看到"打字卡顿"（TPOT 抖动）
- Chunked Prefill（前文）缓解了但不能根除：token 预算的分配本质是两种负载在一张卡上抢资源
- 两类负载的最优 batch size、并行策略都不同，混部只能取折中值

## 分离架构 ★

- **Prefill 集群**：优化目标为算力利用率（高 batch、可以张量并行拉满算力）
- **Decode 集群**：优化目标为显存容量与带宽（KV Cache 池最大化）
- 流程：请求 → Prefill 节点算完首 token 和全部 KV → **KV Cache 传输**到 Decode 节点 → Decode 节点逐 token 生成

收益：

- 两类负载各自用最优配置，TTFT 和 TPOT 可同时逼近各自极限
- 独立扩缩容：流量里长 prompt 多就扩 prefill，长回答多就扩 decode——资源投放精确到负载画像
- SLO 更容易守：研究表明在满足同等 SLO 下，分离架构的吞吐（goodput）可显著高于混部

## 代价与挑战

1. **KV Cache 传输**：长上下文的 KV 是几十 GB 级，必须在毫秒级经 RDMA 传到 decode 侧，否则 TTFT 收益被吃掉。这是 PD 分离最大的工程门槛。
2. **系统复杂度翻倍**：两套集群、路由层、KV 生命周期管理、双端容错。
3. **小流量不划算**：固定开销大，规模不到一定程度时混部 + Chunked Prefill 更经济。

## 决策框架

- 日均请求量小、上下文短 → 混部够了。
- 高并发、长上下文、严格 SLO（如在线客服、实时助手）→ PD 分离。
- 观察信号：混部下 TTFT 和 TPOT 的 p99 无法同时达标、且资源画像分裂（prefill 时算力满、decode 时带宽满）——这是该分家的明确信号。

## 与运维经验的映射

这和你做过的"读写分离""动静分离"是同一个架构思想：负载画像不同的东西分开部署、独立伸缩、之间用高速通道连接。AI Infra 的新鲜在对象（KV Cache 代替了数据库读副本），思想是旧的。
