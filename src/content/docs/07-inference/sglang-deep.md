> vLLM 是推理引擎的"通用主力"，SGLang 则是为复杂 LLM 程序（Agent、多轮调用、结构化输出）优化的另一极。两个都懂，选型才有底气。

## SGLang 的定位

SGLang 出身学术界（UC Berkeley 系），设计目标是**让"LLM 程序"跑得高效**：一个 Agent 任务可能是几十次带分支、带循环、带结构化约束的模型调用，而不是一次问答。它的两个核心技术都服务于这个目标。

## 核心技术一：RadixAttention ★

vLLM 的前缀缓存按"块内容哈希"命中；SGLang 用**基数树（Radix Tree）**组织 KV Cache：

- 树的边是 token 序列，节点存对应的 KV Cache。
- 新请求来时沿树匹配最长前缀——匹配的是"任意位置分叉的前缀"，而不只是从头开始的固定块。
- 多轮对话、Agent 多分支调用（同一上下文派生多个子调用）场景下，共享率显著更高。

类比：vLLM 的前缀缓存是"整页缓存"，RadixAttention 是"目录树式缓存"——分支越多越能体现优势。

## 核心技术二：约束解码与结构化输出

LLM 程序里大量需要"输出必须是合法 JSON / 必须符合某个 schema"。SGLang 把约束编译成**有限状态机**，解码时每一步只允许合法的下一个 token：

- 输出格式 100% 合法——不用重试、不用解析兜底
- 跳过不可能的分支还能提速（搜索空间被裁剪）

对比裸调 API 的"祈祷式 JSON"（提示词要求 + 出错重试），这是工程可靠性的质变。vLLM 后续也跟进支持了 guided decoding，选型时确认所用版本。

## 运行时差异速览

| 维度 | vLLM | SGLang |
| --- | --- | --- |
| 前缀缓存 | 块哈希 | Radix Tree，分支场景更强 |
| 结构化输出 | 支持（guided decoding） | 原生核心能力，深度集成 |
| 生态与社区 | 最大 | 较小但活跃 |
| 生产成熟度 | 最成熟，大厂验证多 | 快速增长中 |
| 编程模型 | OpenAI 兼容 API 为主 | API + 前端领域语言（可写复杂调用程序） |

## 运维关注点

- SGLang 的 Radix Tree 缓存有自己的容量与淘汰策略，监控 radix cache 命中率——Agent 负载下它是最重要的性能指标。
- 结构化输出把"格式错误"这类工单直接清零，值得在 SDK 层统一启用。
- 两者都支持 OpenAI 兼容 API，**网关层抽象好之后，引擎可以互换压测**——别让自己被单一引擎锁死。
