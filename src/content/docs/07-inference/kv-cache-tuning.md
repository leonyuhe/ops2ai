> 长上下文 + 高并发时代，KV Cache 是推理服务的显存大头。围绕它的优化已经发展成一门专项技术。

## 先回忆账本

KV 显存 = 2 × 层数 × KV头数 × 头维度 × 序列长度 × 字节数 × 并发。优化手段无非对这四个乘数动刀：头数（架构选型 GQA/MLA）、长度（驱逐/截断）、字节数（量化）、驻留位置（分层存储）。

## 手段一：KV Cache 量化 ★

把 K/V 从 FP16 降到 FP8 甚至更低：

- 显存直接减半，同卡并发容量近似翻倍。
- 精度风险小于权重量化（K/V 的动态范围相对温和），但要过评测门禁。
- 工程细节：按通道分组 scale、保留少量全精度残留（recent window）是当前主流做法；跳层策略（部分层不量化）可进一步保精度。

## 手段二：驱逐与压缩策略

不是所有历史 token 都同等重要：

- **滑动窗口**：只保留最近 W 个 token 的 KV（Mistral 系架构原生支持）——显存从 O(上下文) 变 O(W)。
- **重要性驱逐**：按注意力分数保留"被关注多"的 token，驱逐冷 token（H2O 等思路）。
- **前缀复用**：重复前缀只存一份（前文前缀缓存已讲）。
- 代价都是信息丢失：被驱逐的内容模型就"忘了"，长文档问答场景慎用。

## 手段三：分层存储（CPU 卸载）

把暂时不活跃的 KV 从 GPU 显存卸载到主机内存（甚至 NVMe），需要时再取回：

- 显存容量约束被松绑一个量级，适合"长会话但访问有局部性"的场景（聊天历史、Agent 长任务）。
- 关键在**预取时机**：取回晚了直接打进 TTFT/TPOT——需要预测性调度。
- Mooncake 等系统就是围绕"KV Cache 作为一等公民的分布式缓存"来设计整站架构的。

## 手段四：架构层选择（选型时就要想清楚）

- GQA：KV 头数砍几倍，显存同比例省——现代模型标配。
- MLA（DeepSeek/Kimi）：把 KV 压成低秩潜向量再缓存，比 GQA 更激进。
- 这些是模型选型期的决策：Infra 团队参与模型选型时，KV Cache 的显存账应该摆上桌。

## 调优顺序建议

1. 先开前缀缓存和合理 max_model_len（免费收益）。
2. 显存仍紧 → KV FP8 量化 + 评测门禁。
3. 长会话负载 → 滑动窗口/分层存储方案评估。
4. 所有手段上线前后跑同一组长上下文压测：TTFT、TPOT、并发容量、答案质量四维对照。
