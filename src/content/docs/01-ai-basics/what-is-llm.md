> 本文的目标：读完能向任何人讲清"大模型是怎么工作的"，且不被营销话术带偏。

## 先给一个不精确但好用的类比

把大语言模型（LLM）想象成一个**见过了整个互联网的补全引擎**。你给它一段文字，它预测"下一个最可能接什么字"。它不理解世界，但它读过关于世界的几乎所有文本，所以它的"猜测"在绝大多数情况下好用到看起来像理解。

这个类比的推论很重要：

- 它没有"知道/不知道"的开关——它永远会给你一个答案，包括编造的（这就是**幻觉**）。
- 它的输出是逐字（逐 token）生成的，就像流水线上一次出一颗珠子——这解释了后面所有的性能问题。

## Token：模型的"字节"

模型不吃文字，吃 token。可以粗糙地把 token 理解成"字词的碎片"：中文里一个字可能是一到两个 token，英文里一个单词平均不到一个 token。

运维需要记住的不是定义，而是两个账本事实：

- **API 按 token 计费**，prompt 和回答都算钱。
- **上下文窗口有限**：模型一次能看到的 token 总数有上限（如 128K）。窗口满了，最早的内容就被挤出视野——和你管理环形日志缓冲区的思路一样。

## 训练管线：一个模型是怎么被造出来的

1. **预训练**：读海量文本学预测下一个 token。成本数百万到数亿美元，产出"基座模型"。基座模型只会续写，不会对话。
2. **指令微调（SFT）**：用"指令-回答"样本教它按人类要求作答。至此它会聊天了。
3. **偏好对齐（RLHF/DPO）**：用人类反馈或偏好数据让它更有用、更安全。
4. **推理强化（可选）**：在数学、代码这类可自动判对错的任务上做强化学习，得到"会先想再答"的推理模型。

运维视角的记忆钩子：这是一条标准的**流水线**——每阶段有输入产物、处理、输出产物和质检，和你熟悉的发布流水线同构。

## Prompt、温度与流式输出

- **Prompt**：你给模型的全部输入。系统提示（system prompt）是"全局配置"，用户消息是"请求体"。
- **Temperature**：控制输出随机性的旋钮。0 = 永远选最可能的下一个词（确定性强、适合严肃任务）；越高越发散（适合创意）。
- **流式输出（streaming）**：模型本来就逐 token 生成，边生成边推送能大幅降低用户的感知延迟——这和你在 Nginx 上调 chunk 传输是一个道理。

## 幻觉：不是 bug，是特性

模型编造事实时没有恶意也没有报错——因为它的目标函数从来就是"像那么回事"，而不是"是真的"。工程上的对策：

- **RAG**：先检索真实文档，让模型基于证据回答（给它开卷考试）。
- **验证器**：对可判对错的任务（数学、代码），用程序检查答案。
- **引用与溯源**：要求模型给出答案依据的原文出处。

作为运维，你要建立的本能是：**凡涉及事实的 AI 输出，都必须有验证或溯源机制**。这和"凡监控指标必须有告警阈值"是同级别的纪律。

## 动手清单

1. 用 curl 直接调一次大模型 API，观察返回结构和 token 计数。
2. 同一个问题分别用 temperature=0 和 1 各问三次，对比输出差异。
3. 故意问一个你熟悉领域的冷门问题，观察幻觉长什么样。
