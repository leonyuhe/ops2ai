> 你不需要会推 Transformer 的公式才能做 AI Infra，但你需要知道计算量和显存花在哪——那是你调优的对象。

## 一句话理解

Transformer 的每一层做两件事：**注意力（Attention）**负责"信息在 token 之间流动"，**前馈网络（FFN）**负责"对每个 token 独立地做知识加工"。一层摞一层（几十上百层），信息逐层提炼。

## 注意力：为什么它是性能优化的主战场

把一句话里的每个 token 想象成总线上的一个设备：注意力让**每个设备都监听所有其他设备**，并决定该听谁多一点。

代价：N 个 token 两两交互，计算量是 N² 级别。推论：

- 输入越长，注意力越贵——长上下文服务的成本高得不是线性的。
- 这个 N² 是推理优化的核心战场：FlashAttention、稀疏注意力、滑动窗口注意力都是在打它的主意。

## KV Cache：推理服务的显存大头

生成第 100 个字时，前 99 个字的注意力中间结果（Key/Value）还要用。为了不重算，系统把它们缓存起来——这就是 KV Cache。

运维账本（这个公式值得背）：

```
KV 显存 ≈ 2 × 层数 × KV头数 × 头维度 × 序列长度 × 字节数 × 并发请求数
```

关键洞察：**KV Cache 随并发和上下文长度线性增长**。70B 级模型在 128K 上下文下，单请求的 KV 缓存就是几十 GB 量级。这就是为什么推理服务的容量规划本质上是显存规划，也是为什么 GQA/MLA/量化这些省显存技术如此值钱。

## 前馈网络：显存里躺着的静态大户

FFN 是每层里最大的参数仓库（大约占模型总参数的 2/3）。它不参与 token 间交互，计算模式是规整的大矩阵乘——GPU 最喜欢的那种。模型权重的显存占用 = 参数量 × 每参数字节数（FP16 是 2 字节），7B 模型 FP16 约 14 GB，这是静态的、可预测的。

## 生成过程的两副面孔：Prefill 与 Decode ★

这是做推理运维必须建立的第一直觉：

- **Prefill（读题）**：一次性并行处理你输入的全部 token。计算密集，GPU 算力是瓶颈。
- **Decode（逐字回答）**：每次只生成一个 token，每步都要把全部权重从显存搬一遍。**显存带宽是瓶颈**，算力大部分闲置。

推论（面试高频）：

- Decode 阶段加大 batch 几乎白捡吞吐——瓶颈在搬权重，多算几个请求不多搬。
- Prefill 和 Decode 抢资源会互相拖累——这是"PD 分离"架构的动机。
- 首字延迟（TTFT）由 Prefill 决定，后续流畅度（TPOT）由 Decode 决定——两类延迟要分开监控、分开优化。

## 看完记住这五句话

1. 注意力是 N² 的，长上下文贵在这里。
2. KV Cache 随并发×上下文线性涨，容量规划就是显存规划。
3. 权重显存是静态账，KV 显存是动态账。
4. Prefill 拼算力，Decode 拼带宽。
5. TTFT 和 TPOT 是两个 SLO，不是一个。
