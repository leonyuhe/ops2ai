> 大多数 CUDA kernel 的性能瓶颈不是算得太慢，而是数据喂得太慢。访存优化是 CUDA 性能工程的第一杠杆。

## 五种内存的职责速查

| 内存 | 作用域 | 速度 | 典型用途 |
| --- | --- | --- | --- |
| 寄存器 | 单线程 | 最快 | 局部变量 |
| 共享内存 | block 内共享 | 快几十倍于全局 | block 内数据复用、tile 暂存 |
| 全局内存（HBM） | 全 GPU | 基准 | 大数据本体 |
| 常量内存 | 全 GPU 只读 | 有缓存加速 | 配置参数 |
| 局部内存 | 单线程（溢出到全局） | 慢 | 寄存器放不下的局部量 |

记住上篇的黄金法则：HBM 带宽是稀缺资源。所有访存优化的目标都是**减少去 HBM 取数的次数，或让每次取数更高效**。

## 合并访问（Coalescing）：最重要的一个概念 ★

GPU 从全局内存取数以 32 字节/128 字节的事务为单位。一个 Warp 的 32 个线程如果访问**连续的 32 个地址**，一次事务搞定；如果跳着访问，最多拆成 32 次事务——带宽浪费 32 倍。

类比：一班车拉 32 个相邻工位的物料只要跑一趟；如果 32 个人要的物料散落在仓库各处，车要跑 32 趟。

代码层面的判定：threadIdx.x 相邻的线程，访问地址是否相邻？相邻即合并。结构体数组（AoS）经常破坏合并访问，改成数组结构体（SoA）即修复。

## 共享内存：程序员手管的缓存

共享内存是 CUDA 优化区别于 CPU 优化的最大特色——它完全由你手动控制：

```cpp
__shared__ float tile[256];   // block 内所有线程可见
tile[threadIdx.x] = gdata[i]; // 从全局搬一次
__syncthreads();              // block 内同步
// 之后任意复用 tile，不再碰全局内存
```

两个使用纪律：

1. **`__syncthreads()` 不能少**：写和读之间必须同步，否则读到别人没写完的数据——这是最经典的 CUDA bug，且不必然报错，只表现为结果偶发错误。
2. **小心 bank conflict**：共享内存分 32 个 bank，同一 Warp 的线程访问同一 bank 的不同地址会串行化。常用解法：数组加 1 个 padding 错位。

## 寄存器压力与溢出

每个 SM 的寄存器总量固定（65536 个）。kernel 用的寄存器越多，SM 上能同时驻留的线程越少（占用率下降）。局部数组过大、循环不展开失控都会导致"寄存器溢出到局部内存"——性能断崖。用 `--ptxas-options=-v` 编译可以看到每个 kernel 的寄存器用量，这是 CUDA 版的"看资源水位"。

## 统一内存（Unified Memory）：便利与代价

`cudaMallocManaged` 分配的内存 CPU/GPU 都能直接访问，缺页时自动迁移。写原型很爽，但自动迁移的开销不可控——生产 kernel 还是显式 memcpy，把数据移动摆到明处。

## 优化检查清单

- Warp 内访存是否连续合并？（不合并 → 改数据布局）
- 数据是否被复用？（复用 ≥2 次 → 值得搬进共享内存）
- 有没有 bank conflict？（Nsight Compute 可查）
- 寄存器用量是否压垮了占用率？
- 主机↔显存传输是否被计算重叠？（多流 + 异步拷贝）
