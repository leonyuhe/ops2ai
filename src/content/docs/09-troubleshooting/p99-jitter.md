> p99 是推理服务的照妖镜：均值好看不等于用户舒服。本文四个案例覆盖 80% 的尾延迟根因。

## 案例一：长 Prompt 的 Prefill 阻塞 Decode

**现象**：TTFT 正常，TPOT 的 p99 间歇飙升，用户感知"打字卡顿"。
**根因**：混部模式下，长文档请求的大 prefill 抢占了 decode 资源。
**修复**：开启 Chunked Prefill（token 预算混编）；规模大则上 PD 分离。
**教训**：TTFT 和 TPOT 是两个 SLO，要分开监控分开治理。

## 案例二：前缀缓存集体失效

**现象**：版本发布后整体 TTFT 翻倍，吞吐没变。
**根因**：新版本的 system prompt 改了一个字——所有请求前缀不再逐 token 一致，前缀缓存命中率从 90% 跌到 5%，每次请求都重新 prefill 全部系统提示。
**修复**：固定前缀部分，变更部分后置；发布门禁加入"前缀命中率"指标。
**教训**：前缀缓存依赖逐 token 一致，prompt 变更 = 缓存架构变更，要走评审。

## 案例三：批大小把延迟顶爆

**现象**：高峰期 p99 延迟陡增，但单请求测试一切正常。
**根因**：为提吞吐把 max batch 调大，单步 decode 计算量随之增大，TPOT 随并发线性劣化——吞吐和延迟的拐点被顶穿。
**修复**：用压测曲线找拐点（SLO 内的最大并发），把并发上限钉在拐点前；排队比硬塞更保护 p99。
**教训**：吞吐最大化和延迟最小化是两个方向，SLO 是裁判。

## 案例四：CPU 侧隐形瓶颈

**现象**：GPU 利用率不高但延迟降不下来，加卡无效。
**根因**：decode 小 kernel 密集，CPU 发射跟不上（或调度器/分词等 CPU 环节拖后腿）。
**修复**：CUDA Graph 回放、分词异步化、CPU 绑核；Nsight Systems 时间线确认 GPU 空隙来源。
**教训**：推理服务是 CPU+GPU 联合系统，盯着 GPU 调优可能完全搞错对象。

## 通用排查剧本 ★

1. **分层**：网关 / 队列 / prefill / decode 各段耗时打点，先定位段。
2. **分位**：每段都看 p50/p95/p99——均值会撒谎。
3. **对比**：与昨日/上周同期对比，先回答"什么变了"（发布、流量、负载画像）。
4. **下钻**：队列段 → 容量；prefill 段 → 输入长度分布与缓存命中率；decode 段 → batch 与 CPU 开销。
5. **留证**：火焰图/时间线截图入事故报告，沉淀进本案例库。

## 预防性监控

- 分段延迟分位数全量打点
- 前缀缓存命中率、KV Cache 水位、抢占次数入看板
- 发布门禁：固定负载压测，p99 退化 >5% 拦截
