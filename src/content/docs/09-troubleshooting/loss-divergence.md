> Loss 发散像服务器宕机：表现只有一个，根因有一族。本文给你一棵排查决策树。

## 三种形态先分清

- **缓慢发散**：loss 持续爬升——多为学习率过高或优化器配置错误。
- **突刺（spike）**：某一步突然冲高后可能回落也可能不回落——多为异常数据或数值溢出。
- **NaN/Inf**：loss 直接变非数——数值溢出的终局形态。

## 排查决策树 ★

### 第一层：数据（先查这个，成本最低）

- 发散时间点对应的 batch 是什么？把该 batch 样本打出来看：乱码、超长、异常标签是常客。
- 数据管道最近变更过吗？新数据源、新预处理脚本都是嫌疑人。
- 对策：加数据校验（长度、字符集、标签范围），异常样本跳过并告警。

### 第二层：数值精度

- FP16 溢出？（梯度爆炸）→ 换 BF16 或检查 Loss Scaling。
- 梯度范数（grad norm）监控开了吗？发散前通常先有 grad norm 飙升——它是比 loss 更早的预警信号。
- 对策：梯度裁剪（clip）是否启用、阈值是否合理。

### 第三层：超参与配置

- 学习率：warmup 是否过短、峰值是否过大、调度器配置是否正确。
- 混合精度配置变更、优化器状态在新旧 checkpoint 间不匹配（恢复训练时常见）。
- 框架/库版本升级后发散 → 先怀疑默认行为变化，用旧版本对照跑。

### 第四层：模型与架构

- 注意力 logits 爆炸（超长上下文、某些归一化配置下）。
- 新增模块（新归一化、新激活）的数值稳定性。

## 抢救与止损

- **回退到发散前的 checkpoint** + 降低学习率 + 跳过坏数据段——标准抢救三连。
- 长训任务的保险：定时 checkpoint + loss/grad norm 异常自动暂停——宁可暂停等人看，不要狂奔烧算力。
-  spike 频发时考虑"spike 检测自动回滚"：检测突刺 → 回滚最近 checkpoint → 跳过该数据区间继续。

## 预防性监控清单

| 指标 | 告警逻辑 |
| --- | --- |
| loss | 环比突增（如 >3σ） |
| grad norm | 超阈值或趋势性爬升 |
| 吞吐（tokens/s/GPU） | 异常下降（往往是隐性故障先兆） |
| 数据校验失败率 | 任何非零都值得看 |
